# 아키텍처

## 데이터 흐름

```
┌─────────────────────────────┐
│  바이낸스 aggTrade WebSocket │   실시간 체결 스트림
└──────────────┬──────────────┘
               │  체결 하나하나
               ▼
┌─────────────────────────────┐
│      1초 버킷 집계          │   { startMs, quoteVolume, tradeCount }
└──────────────┬──────────────┘
               │  1초 해상도 시계열
               ▼
┌─────────────────────────────┐
│    프레임별 롤링 창 계산     │   1m / 5m / 15m / 1h / 4h / 1d
│                             │   v = 누적 거래대금 / 경과분
└──────────────┬──────────────┘
               │  RollingWindow
               ▼
┌─────────────────────────────┐
│   중앙값 / MAD 기준선        │   M = median(직전 N개 v)
│   점수 S 계산               │   D = median(|v - M|)
│                             │   S = (v - M) / D
└──────────────┬──────────────┘
               │  AnomalyScore
               ▼
┌─────────────────────────────┐
│      퍼센타일 환산          │   심볼·프레임별 과거 S 분포 기준
└──────────────┬──────────────┘
               │  percentile (0~100)
               ▼
┌─────────────────────────────┐
│      채널별 임계 판정        │   채널마다 민감도가 다르다
└──────────────┬──────────────┘
               │  AlertCandidate (채널 × 종목 × 프레임)
               ▼
┌─────────────────────────────┐
│      필터 (채널 단위)        │
│   1. 최소 거래대금 컷        │   진입 불가한 잡코인 제거
│   2. 워밍업 (최소 경과 시간) │   표본 부족 구간 제외
│   3. 시간 감쇠 쿨다운        │   같은 사건 반복 발사 억제
│   4. 프레임 병합            │   1m/5m/15m 동시 발화를 하나로
└──────────────┬──────────────┘
               │  MergedAlert
               ▼
┌─────────────────────────────┐
│          발송               │
│   브라우저 (탭 열림) / 텔레그램  │   채널이 고른 수단으로 동시 발송
└─────────────────────────────┘
```

### 채널이 파이프라인을 가르는 지점

위 그림에서 **"채널별 임계 판정" 위쪽은 채널과 무관하다.** 점수 S와
퍼센타일은 종목·프레임의 성질이지 사용자 설정의 함수가 아니다.
민감도가 90이든 99.9든 같은 S가 나온다.

그래서 detector는 무거운 계산(1초 버킷, 롤링 창, 중앙값/MAD, 퍼센타일)을
**종목당 한 번만** 하고, 그 결과를 채널마다 다른 임계에 통과시킨다.
채널이 100개여도 무거운 부분은 종목 수만큼만 돈다.

쿨다운과 병합은 반대로 채널마다 독립이어야 한다. 같은 코인을 두 채널이
감시할 때 한쪽에서 알림이 나갔다고 다른 쪽이 조용해지면 안 된다.
상태 키가 `SeriesKey`가 아니라 `ChannelSeriesKey`인 이유다.

이 구조는 `apps/backtest`에서 먼저 검증됐다. 백테스트도 같은 이유로
교차 추출(무겁다)과 파라미터 평가(가볍다)를 나눈다.

각 단계의 인터페이스는 `packages/core/src/types.ts`에 선언되어 있다.
구현체는 아직 없다.

## 컴포넌트

### apps/detector

상시 구동 프로세스. 파이프라인 전체를 담당한다.

- 바이낸스 WebSocket 연결 유지와 재연결
- 1초 버킷 집계, 프레임별 롤링 창 평가 (1초 틱)
- 점수 계산, 퍼센타일 환산 (종목당 한 번)
- 채널별 임계 판정과 필터 체인
- 발송: 텔레그램 직접, 브라우저는 열려 있는 세션으로 밀어주기
- 헬스체크 HTTP 엔드포인트

알림이 브라우저에서 울려도 감지를 브라우저에서 할 수는 없다.
퍼센타일 환산에 14일치 S 분포가 필요한데 탭을 닫으면 그게 유지되지 않는다.
서버가 계속 돌면서 감지하고, 브라우저는 결과를 받아 띄우기만 한다.

### apps/web

사용자 대면 UI. 감지에는 관여하지 않는다.

- 채널 생성 / 편집 / 삭제
- 채널마다: 코인 묶음 선택, 민감도 슬라이더, 전달 수단 선택
- 텔레그램 연동 (계정 단위, 채널이 골라 쓴다)
- 알림 히스토리 대시보드
- **알림 수신**: 탭이 열려 있는 동안 서버와 연결을 유지하고,
  알림이 오면 Notification API로 띄운다

브라우저 알림은 탭이 닫히면 끊긴다. 탭이 닫혀도 받으려면 Web Push
(서비스 워커 + VAPID)가 필요한데 지금은 범위 밖이다. 그래서 텔레그램을
같이 켜두는 것이 기본 사용 방식이다.

### apps/backtest

파라미터를 확정하기 위한 오프라인 도구다. 배포되지 않는다.

바이낸스 공개 덤프(1초 kline)를 내려받아 이진 형식으로 변환하고,
detector와 같은 순서로 리플레이한다. 실행은 2단계로 나뉜다.

1. **교차 추출** — 1초 시계열을 훑어 임계를 넘은 (초, 프레임)만 뽑아
   캐시한다. 종목당 1분 안팎으로 무겁다.
2. **파라미터 스윕** — 캐시된 교차에 쿨다운·병합 조합을 훑는다.
   조합당 수십 밀리초라 수십 개를 한 번에 비교할 수 있다.

S 계산과 퍼센타일 환산은 쿨다운·병합 파라미터와 무관하므로, 나눠두면
같은 계산을 반복하지 않는다.

실시간은 aggTrade를 쓰지만 백테스트는 1초 kline을 쓴다. 해상도가 같고
용량이 1/7이다 (BTCUSDT 월 68MB vs 475MB).

### packages/core

두 앱이 공유하는 것만 넣는다.

- 도메인 타입 (`Timeframe`, `AnomalyScore`, `MergedAlert` 등)
- 상수 (프레임 목록, 민감도 범위, 백테스트 대상 파라미터)
- 알고리즘 인터페이스 선언

web은 알림 히스토리를 렌더링할 때 detector가 만든 것과 **같은 타입**을
읽어야 하고, 민감도의 의미도 양쪽이 동일하게 해석해야 한다. 그래서
타입과 상수를 공유 패키지로 뺐다.

## 배포 구성

```
┌──────────────┐        ┌───────────────────────┐
│    Vercel    │        │  Railway / Fly.io     │
│              │        │  (도쿄 리전)          │
│  apps/web    │        │  apps/detector        │
│  Next.js 15  │        │  상시 Node 프로세스   │
└──────┬───────┘        └───────────┬───────────┘
       │                            │
       │   설정 읽기/쓰기            │  aggTrade WS
       └────────► DB ◄──────────────┘        │
                                             ▼
                                    바이낸스 (AWS 도쿄)
```

### web은 Vercel

Next.js App Router 기본 배포처다. 특별한 이유가 없다.

### detector는 서버리스 불가

detector는 WebSocket을 상시 열어두고 1초마다 평가를 돈다. 서버리스
함수는 요청 단위로 뜨고 지므로 이 모델에 맞지 않는다. 실행 시간 제한도
걸린다. 상시 프로세스를 돌릴 수 있는 곳이 필요하다.

### 리전은 도쿄

바이낸스 매칭 엔진이 AWS 도쿄 리전에 있다. 리전 선택이 지연에 직결된다.

| 배포 리전 | 왕복 지연 |
|---|---|
| 도쿄 | 10~20ms |
| 서울 | 40~60ms |
| 미국 | 150ms+ |

급등 알림은 몇십 ms 차이가 진입가에 반영되는 도구다. 서울이 물리적으로
가깝다는 이유로 서울을 고르면 안 된다. 거래소가 어디 있는지가 기준이다.

Railway와 Fly.io 둘 다 도쿄 리전을 지원한다. 어느 쪽을 쓸지는 아직
정하지 않았다.

## 상태 저장

아직 확정하지 않았다. 다음 세션 이후 결정할 항목이다.

- 사용자 설정 (감시 종목, 민감도, 텔레그램 연동)
- 알림 히스토리
- 퍼센타일 환산용 과거 S 분포

앞의 둘은 web과 detector가 함께 읽고 쓰므로 공용 DB가 필요하다.
마지막 하나는 detector가 매 초 접근하므로 프로세스 인메모리에 두고
주기적으로만 영속화하는 편이 맞을 가능성이 높다.
